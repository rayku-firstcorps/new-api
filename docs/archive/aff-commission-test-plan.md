# 推广返佣功能测试用例 PRD

## 测试范围

本文档覆盖推广（aff）系统充值返佣功能的完整测试，包括后端逻辑、前端管理配置、端到端流程。

---

## 一、测试环境

| 项目 | 配置 |
|------|------|
| 部署方式 | Docker Compose 本地部署 |
| 访问地址 | http://localhost:3000 |
| 数据库 | PostgreSQL 15 |
| 缓存 | Redis |
| 管理员账号 | root（初始密码 123456） |

---

## 二、前置条件

1. 服务正常运行（`/api/status` 返回 success: true）
2. 管理员已登录后台
3. 已在「支付网关」设置中确认合规声明（Payment Compliance Confirmed）

### 模块 B：邀请注册流程

#### B-1：获取邀请链接

| 步骤 | 操作 | 预期结果 |
|------|------|----------|
| 1 | 用户 A 登录 → 钱包页面 | 显示推荐计划卡片 |
| 2 | 查看邀请链接 | 格式为 `http://localhost:3000/sign-up?aff=XXXX` |
| 3 | 点击复制按钮 | 链接复制到剪贴板 |

#### B-2：通过邀请链接注册

| 步骤 | 操作 | 预期结果 |
|------|------|----------|
| 1 | 打开用户 A 的邀请链接 | 跳转到注册页面 |
| 2 | 用户 B 填写注册信息并提交 | 注册成功 |
| 3 | 检查用户 B 的 inviter_id | 等于用户 A 的 ID |
| 4 | 检查用户 A 的 aff_count | +1 |
| 5 | 若 QuotaForInvitee > 0 | 用户 B 获得对应额度 |
| 6 | 若 QuotaForInviter = 0 | 用户 A 的 aff_quota 不变（不再注册即送） |

#### B-3：OAuth 注册绑定邀请关系

| 步骤 | 操作 | 预期结果 |
|------|------|----------|
| 1 | 打开邀请链接 → 选择 GitHub/Discord 登录 | OAuth 流程正常 |
| 2 | 首次 OAuth 登录自动创建账号 | 新用户的 inviter_id 正确关联 |

### 模块 C：充值返佣核心逻辑

#### C-1：正常返佣（管理员补单模拟）

**前置**：AffCommissionRate = 10，其他返佣配置为 0

| 步骤 | 操作 | 预期结果 |
|------|------|----------|
| 1 | 用户 A 邀请用户 B 注册 | 邀请关系建立 |
| 2 | 管理员为用户 B 创建充值订单（金额 $10） | 订单创建成功 |
| 3 | 管理员手动完成该订单 | 用户 B 余额增加 |
| 4 | 检查用户 A 的 aff_quota | 增加 = $10 对应 quota × 10% |
| 5 | 检查用户 A 的 aff_history | 同步增加 |
| 6 | 检查系统日志 | 记录"邀请用户充值返佣"日志 |

#### C-2：返佣比例为 0 时不触发

**前置**：AffCommissionRate = 0

| 步骤 | 操作 | 预期结果 |
|------|------|----------|
| 1 | 用户 B 充值成功 | 用户 A 的 aff_quota 不变 |
| 2 | 系统日志 | 无返佣相关日志 |

#### C-3：首充门槛测试

**前置**：AffCommissionRate = 10，AffFirstTopupMinAmount = 1000（$10）

| 步骤 | 操作 | 预期结果 |
|------|------|----------|
| 1 | 用户 B 首次充值 $5（500 分） | 不满足门槛，用户 A 无返佣 |
| 2 | 检查用户 B 的 aff_first_topup_passed | 仍为 false |
| 3 | 用户 B 再次充值 $10（1000 分） | 满足门槛，用户 A 获得返佣 |
| 4 | 检查用户 B 的 aff_first_topup_passed | 变为 true |
| 5 | 用户 B 第三次充值 $3（300 分） | 已通过门槛，正常返佣 |

#### C-4：有效期过期测试

**前置**：AffCommissionRate = 10，AffCommissionDurationDays = 1

| 步骤 | 操作 | 预期结果 |
|------|------|----------|
| 1 | 用户 B 注册后立即充值 | 用户 A 获得返佣 |
| 2 | 修改用户 B 的 created_at 为 2 天前（数据库直接修改） | — |
| 3 | 用户 B 再次充值 | 用户 A 不获得返佣（已过期） |

#### C-5：单笔上限截断

**前置**：AffCommissionRate = 50，AffCommissionMaxPerTopup = 1000000（$2）

| 步骤 | 操作 | 预期结果 |
|------|------|----------|
| 1 | 用户 B 充值 $100 | 理论返佣 = $50 对应 quota |
| 2 | 检查用户 A 实际获得 | 被截断为 1000000（$2） |

#### C-6：无邀请人不触发

| 步骤 | 操作 | 预期结果 |
|------|------|----------|
| 1 | 用户 C 自行注册（无 aff 参数） | inviter_id = 0 |
| 2 | 用户 C 充值 | 无任何返佣逻辑触发 |

#### C-7：多次充值累计返佣

**前置**：AffCommissionRate = 10

| 步骤 | 操作 | 预期结果 |
|------|------|----------|
| 1 | 用户 B 充值 $10 | 用户 A 获得 10% 返佣 |
| 2 | 用户 B 再充值 $20 | 用户 A 再获得 10% 返佣 |
| 3 | 检查用户 A 的 aff_quota | 等于两次返佣之和 |
| 4 | 检查用户 A 的 aff_history | 等于两次返佣之和 |

### 模块 G：多支付渠道覆盖

对以下每个支付渠道，验证充值成功后均能触发返佣：

| 渠道 | 函数 | 验证方式 |
|------|------|----------|
| Stripe | Recharge | Webhook 回调 |
| 管理员补单 | ManualCompleteTopUp | 后台手动操作 |
| Creem | RechargeCreem | Webhook 回调 |
| Waffo | RechargeWaffo | Webhook 回调 |
| Waffo Pancake | RechargeWaffoPancake | Webhook 回调 |
| Airwallex | RechargeAirwallex | Webhook 回调 |
| Payssion | RechargePayssion | Webhook 回调 |

> 本地测试优先使用「管理员补单」验证核心逻辑，其他渠道可通过单元测试覆盖。

## 五、自动化测试建议

### 单元测试（Go test）

建议在 `model/aff_commission_test.go` 中覆盖：

```go
func TestTryGrantAffCommission_NoInviter(t *testing.T)           // inviter_id=0 不触发
func TestTryGrantAffCommission_RateZero(t *testing.T)            // rate=0 不触发
func TestTryGrantAffCommission_NormalCommission(t *testing.T)    // 正常返佣计算
func TestTryGrantAffCommission_MaxPerTopupCap(t *testing.T)      // 上限截断
func TestTryGrantAffCommission_Expired(t *testing.T)             // 有效期过期
func TestTryGrantAffCommission_FirstTopupThreshold(t *testing.T) // 首充门槛
func TestTryGrantAffCommission_ComplianceNotConfirmed(t *testing.T) // 合规未确认
```

### API 集成测试

使用 `curl` 或 HTTP 测试框架验证：
- `POST /api/user/register` 带 aff 参数
- `GET /api/user/aff` 获取邀请码
- `POST /api/user/aff_transfer` 转入余额
- `PUT /api/option` 保存配置项
