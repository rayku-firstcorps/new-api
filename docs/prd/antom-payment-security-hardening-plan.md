# Antom 支付安全加固实施计划

## 1. 背景与目标

当前 Antom 支付已经具备回调验签、订单状态校验、数据库行锁和重复回调幂等处理。审计发现，Antom 入账路径仍需补齐支付结果字段核对、钱包额度上限和安全数值转换，避免异常订单或极端输入造成错误入账。

本计划只定义加固方案，不改变正常支付的下单、跳转、Webhook、Inquiry 和到账体验。

## 2. 当前调用链

```text
用户确认支付
  -> POST /api/user/antom/pay
  -> 创建 pending TopUp
  -> Antom Pay API
  -> Antom payment_url
  -> Antom webhook 或前端 inquiry
  -> Antom 状态确认
  -> RechargeAntom
  -> TopUp success + 用户 quota 增加
```

现有防线：

- Webhook 使用 Antom 公钥校验 `request-time`、`client-id`、`signature` 和原始请求体。
- 订单必须属于 `PaymentProviderAntom`，且只能从 `pending` 进入 `success`。
- `RechargeAntom` 使用数据库行锁，重复通知不会重复充值。
- Inquiry 通过服务端 Antom Query API 判断支付状态，不接受前端直接提交的 paid 结果。

## 3. 审计发现

### 3.1 入账前未核对支付金额和币种

Webhook 验签成功后，当前实现只依据订单号和 `resultCode == SUCCESS` 调用 `RechargeAntom`。入账函数按本地订单的 `Amount` 增加额度，但没有核对通知或服务端查询结果中的支付金额、币种、商户订单号和买家标识。

加固后必须确认：

- Antom payment request ID 与本地 `TradeNo` 一致；
- Antom reference order ID 与本地 `TradeNo` 一致；
- 支付状态为明确的 `SUCCESS`；
- 支付金额与本地 `TopUp.Money` 按货币精度一致；
- 支付币种与本地订单币种一致；
- 买家标识与本地用户绑定关系一致（若 Antom 返回该字段）。

### 3.2 Antom 入账未复用钱包上限保护

`RechargeAntom` 当前直接执行 `quota + quotaToAdd`，没有复用其他支付路径使用的 `creditTopUpQuota`，也没有使用 `WalletQuotaFromDecimalStrict`。这会让 Antom 路径绕过钱包最大额度和安全整数边界保护。

### 3.3 请求金额缺少最大值边界

`AntomPayRequest.Amount` 目前只检查最小值。极大的 `int64` 输入可能在 `float64` 金额换算、货币最小单位转换或额度转换时产生精度损失和溢出风险。

## 4. 实施步骤

### 步骤一：统一安全金额和额度转换

- 为 Antom 充值数量增加明确的最大值，并在下单入口返回 400 业务错误。
- 使用 `common.WalletQuotaFromDecimalStrict` 将订单金额转换为钱包额度。
- 拒绝负数、零值、NaN、Inf、超过 `common.MaxWalletQuota` 或无法安全转换的结果。
- 保持现有最小充值金额和支付方式校验。

### 步骤二：复用原子钱包入账逻辑

- 将 `RechargeAntom` 的用户余额更新改为 `creditTopUpQuota`。
- 在同一数据库事务中完成订单状态更新和额度增加。
- 保留订单行锁、状态检查和重复回调幂等行为。
- 额度上限失败时，订单保持 pending 或进入明确的人工复核状态，不能标记成功后再失败。

### 步骤三：服务端确认支付结果

- Webhook 验签通过后解析通知字段。
- 对成功通知调用 Antom Query API，确认最终支付状态。
- Inquiry 已经调用 Query API；其入账路径也必须使用同一套金额、币种和订单归属校验。
- Query 返回处理中、未知、失败或字段不完整时不得入账。

### 步骤四：增加通知重放和异常审计

- 保留数据库状态幂等和行锁作为最终防线。
- 记录订单号、用户 ID、金额、币种、Antom 状态、通知来源 IP 和拒绝原因。
- 对金额不匹配、币种不匹配、买家不匹配、订单不存在和重复通知分别记录告警。

## 5. 测试计划

### 后端单元和集成测试

| 场景 | 预期结果 |
|---|---|
| 正常成功通知 | 订单成功，余额增加一次 |
| 重复 Webhook | 不重复增加余额 |
| 验签失败 | 返回失败，不改变订单和余额 |
| `resultCode` 成功但 Query 状态非成功 | 不入账 |
| 金额不一致 | 拒绝入账并记录告警 |
| 币种不一致 | 拒绝入账并记录告警 |
| 订单号或买家不匹配 | 拒绝入账 |
| 已过期/已失败订单 | 不入账 |
| 钱包接近最大额度 | 按上限原子拒绝 |
| 极大充值数量 | 下单阶段拒绝，不调用 Antom |
| 并发 Webhook 和 Inquiry | 最多成功入账一次 |

### 沙箱验证

- 成功支付并返回充值页；
- 取消支付和支付失败；
- Webhook 延迟或重复发送；
- Inquiry 先于 Webhook 到达；
- Query 返回处理中后转成功；
- 金额、币种和订单字段异常；
- 钱包达到上限时支付完成后的处理结果。

## 6. 兼容性和影响

正常订单的下单参数、支付 URL、回调地址、前端轮询和成功页面保持不变。新增校验只会拒绝字段不一致、状态不明确、超出额度上限或数值不安全的订单。服务端 Query 确认会增加一次 Antom API 请求和少量延迟，但不会改变用户支付流程。

## 7. 验收标准

- Antom 正常支付在沙箱和生产配置下均可成功到账。
- 任何验签失败、状态非成功、金额/币种/订单归属不一致的通知都不会增加余额。
- 同一订单并发或重复处理最多增加一次额度。
- Antom 路径使用统一的钱包额度上限和安全转换逻辑。
- 极大金额在创建订单前被拒绝。
- `go test ./...` 通过，相关支付测试覆盖上述场景。
- 变更涉及数据库结算路径时，按项目要求完成 SQLite、MySQL 和 PostgreSQL 验证，并记录版本、命令和结果。

## 8. 回滚方案

代码改动应拆分为金额校验、统一结算和回调字段核对三个可独立回滚的提交。若 Antom 沙箱或生产接口存在字段兼容问题，可暂时关闭新增字段核对并保留签名、状态、行锁、幂等和额度上限保护；不得回滚到绕过数据库状态和原子额度更新的实现。

## 9. 范围边界

本计划不包含：

- 更换 Antom SDK 或支付服务商；
- 修改其他支付渠道的结算逻辑；
- 修改前端支付弹窗行为；
- 修改推广奖励、分佣或订单过期策略；
- 修改 Redis 或数据库部署架构。
